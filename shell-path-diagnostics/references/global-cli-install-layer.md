# Global CLI install layer (macOS)

## Bin directory per manager

| manager | bin dir | authoritative check |
|---|---|---|
| composer 2.x | `~/.composer/vendor/bin` when `~/.composer` exists (legacy), else `~/.config/composer/vendor/bin` | `composer global config bin-dir --absolute` |
| npm | `$(npm prefix -g)/bin` | `npm prefix -g` |
| pnpm | `~/Library/pnpm` and `~/Library/pnpm/bin` | `pnpm root -g` |
| bun | `~/.bun/bin` | `$BUN_INSTALL` |
| pip / pipx | `~/Library/Python/3.x/bin`, `~/.local/bin` | `python3 -m site --user-base` |
| cargo | `~/.cargo/bin` | `$CARGO_HOME` |
| ruby gems | `$(gem env gemdir)/bin` | `gem env` |
| homebrew | `/opt/homebrew/bin`, `/opt/homebrew/sbin` | `brew --prefix` |

## Composer global mechanics

- `COMPOSER_HOME` resolution: the env var if set, else `~/.composer` when that directory already exists, else `~/.config/composer`. Divergence between the env var and `composer global config home` is a classic reason a "successful" global install never reaches PATH.
- Files in `~/.composer/vendor/bin/` are generated PHP proxies (header: `Proxy PHP file generated by Composer`), not symlinks. Each one does `include __DIR__.'/../autoload.php'` and then the package's real bin file.
- A proxy is rewritten only when its owning package is touched, so per-file mtimes in the bin dir differ by package and date. That makes mtime a useful signal: a wrapper timestamped to a recent reinstall did not exist before it.
- Re-requiring an already-installed package still re-syncs binaries. Verified: delete `vendor/bin/laravel`, run `composer global require laravel/installer`, output is `Writing lock file` / `Installing dependencies from lock file` / `Nothing to install, update or remove` / `Generating autoload files`, and the proxy is restored.
- Inventory: `composer global show | grep <name>`. Isolated probe that never touches the real global home: `env COMPOSER_HOME=/tmp/probe composer global require <pkg>`.
- Old composer phars emit long PHP 8.4/8.5 deprecation stacks on every run. Filter them (`2>&1 | grep -viE 'deprecat'`) rather than reading them as failures; `composer --version` still reports the real version.

## Laravel installer quirks

- `laravel` comes from the global package `laravel/installer` (5.x). Other Laravel CLIs are separate global packages: `laravel/pint`, `laravel/valet`, `laravel/lsp`, `laravel-zero/installer`.
- `laravel new` emits machine-readable output - `{"success":true,"name":...,"directory":...}` - instead of the human `Application created successfully` line when it detects it is running inside an AI agent (laravel/agent-detector; `NewCommand` detects agents, suppresses interactive output and emits a JSON result). JSON inside Hermes is expected behavior, not breakage; do not report it as a bug. `laravel --version` behaves identically in every environment and is the right check to quote to the user.
- `laravel new` requires php plus the curl/zip/mbstring/openssl extensions available to that php, and does a full starter-kit install (writes `composer.lock`).

## Clean-environment shell check

    env -i HOME="$HOME" TERM=xterm-256color /bin/zsh -lic 'which <cmd>; <cmd> --version'

Login + interactive zsh with a wiped environment mirrors what a freshly opened terminal tab receives. Use it to prove an rc-file fix landed. The agent's own shell must not be used for that verdict: its PATH is inherited from the parent process and carries both the old and the new state at once.

## Wrapper mtime as evidence

    ls -la ~/.composer/vendor/bin/
    stat -f '%Sm %N' ~/.composer/vendor/bin/<cmd> ~/.composer/vendor/composer/installed.json

A proxy sharing a timestamp with `installed.json` was written by that same install/require run. Older siblings (kept at their own install dates) show that the bin dir is normally stable, which is what makes a fresh timestamp meaningful.
